## Intro

단일 DB에서 복잡한 다단계 비즈니스 흐름을 **ACID 트랜잭션**으로 구현하다 보면, 순수 DB 작업만으로도 트랜잭션이 길어지면서 [락 경합](#락-경합)과 타임아웃이 발생합니다. 인라인 코드는 `SELECT ... FOR UPDATE`처럼 링크와 구분되는 중립색 칩으로 표시됩니다. 한국어 문장은 어절 단위로 줄이 바뀌어 단어가 중간에 잘리지 않습니다. <Badge tone="accent">Astro 7</Badge> <Badge>Pretendard</Badge>

> 트랜잭션의 길이는 곧 락을 쥐고 있는 시간이다. 짧게 끝내는 것이 가장 강력한 동시성 전략이다.

### 락 경합

1. 트랜잭션 A가 `orders` 행에 쓰기 락을 획득합니다.
2. 트랜잭션 B는 같은 행을 기다리며 블로킹됩니다.
   - 대기 시간이 `innodb_lock_wait_timeout`을 넘으면 실패합니다.
   - 재시도 로직이 없다면 사용자 요청이 그대로 실패합니다.
3. A가 커밋해야 B가 진행됩니다.

> [!tip] Saga로 쪼개기
> 긴 트랜잭션을 **로컬 트랜잭션의 연쇄**로 나누고, 실패 시 보상 트랜잭션으로 되돌립니다. 이 콜아웃은 컴포넌트가 아니라 Obsidian `> [!tip]` 문법으로 작성했습니다.

```kotlin title="OrderService.kt"
@Transactional
fun placeOrder(command: PlaceOrderCommand): OrderId {
    val order = Order.create(command.customerId, command.items)
    orderRepository.save(order)
    paymentClient.charge(order.id, order.total) // [!code --]
    eventPublisher.publish(OrderPlaced(order.id)) // [!code ++]
    return order.id // [!code highlight]
}
```

```sql title="schema.sql"
-- 28줄을 넘는 블록은 자동으로 접힌다
CREATE TABLE orders (
    id            BIGINT       PRIMARY KEY,
    customer_id   BIGINT       NOT NULL,
    status        VARCHAR(20)  NOT NULL,
    total_amount  DECIMAL(12,2) NOT NULL,
    created_at    TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE order_items (
    id          BIGINT PRIMARY KEY,
    order_id    BIGINT NOT NULL REFERENCES orders(id),
    product_id  BIGINT NOT NULL,
    quantity    INT    NOT NULL CHECK (quantity > 0),
    unit_price  DECIMAL(12,2) NOT NULL
);

CREATE TABLE saga_log (
    saga_id     UUID        NOT NULL,
    step        VARCHAR(50) NOT NULL,
    status      VARCHAR(20) NOT NULL,
    payload     JSONB,
    created_at  TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (saga_id, step)
);

CREATE INDEX idx_orders_customer ON orders (customer_id, created_at DESC);
CREATE INDEX idx_saga_log_status ON saga_log (status) WHERE status <> 'DONE';
```

## 절차와 비교

<Steps>

1. **보상 트랜잭션 정의**

   각 단계마다 되돌리는 동작을 먼저 설계합니다.

2. **오케스트레이터 구현**

   단계 실행과 실패 시 역순 보상을 한곳에서 관리합니다.

3. **멱등성 보장**

   같은 메시지가 두 번 와도 결과가 같도록 키를 둡니다.

</Steps>

| 방식 | 일관성 | 락 보유 시간 | 복잡도 |
| --- | --- | :---: | ---: |
| 단일 ACID 트랜잭션 | 강한 일관성 | 길다 | 낮음 |
| Saga (Orchestration) | 최종 일관성 | 짧다 | 중간 |
| Saga (Choreography) | 최종 일관성 | 짧다 | 높음 |

<Callout type="warning">
  보상 트랜잭션은 **멱등**해야 합니다. 같은 보상이 두 번 실행되어도 결과가 같아야 합니다.
</Callout>

</Disclosure>
