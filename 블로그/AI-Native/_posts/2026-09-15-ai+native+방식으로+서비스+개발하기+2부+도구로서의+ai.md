## Intro

## AI 에이전트의 첫인상

에이전트에게 일을 맡기고 처음 눈에 띈 건 코드 작성 속도였습니다. API와 도메인 로직을 기존 패턴에 맞춰 만들고 타입 오류나 정적 검사 결과를 보고 다시 고치는 일을 빠르게 처리했습니다.

시간이 좀 지나 돌아보니 인상에 남은 건 그쪽이 아니었습니다. 조건과 목표를 주면, 아직 정하지 않은 선택지가 어디서 갈라지는지를 보여줬습니다. 정책이 여러 조건에 따라 바뀌는 기능에서 이게 특히 달랐습니다.

그다음부터는 결정 트리를 달라고 요청했습니다. 복잡한 문제를 한 번에 정하려고 하면 확인해야 할 게 한꺼번에 몰려왔는데, 트리로 펼쳐놓으면 어느 지점에서 무엇을 정해야 하는지가 눈에 보였습니다.

## 결정 트리: 시뮬레이터로서 AI 에이전트

학원 수강 신청이 익숙한 예입니다. 화면 하나를 그리는 것도 아니고 버튼 하나를 붙이는 것도 아닙니다. 정원을 어디서 판정할지, 동시 신청을 어떻게 막을지, 환불 금액을 언제 확정할지처럼 구현 지점을 정해야 하는 것들입니다. 조건 두세 개만 겹쳐도 경우의 수가 금방 불어납니다. 어디까지 확인했는지 따라가기도 어려워집니다.

기능을 개발하는 입장에서 만나는 결정은 대부분 이런 모습입니다. 제품 요구사항에는 "수강 신청" 한 줄만 적혀 있는데, 그 한 줄을 코드로 옮기려면 갈 곳이 정해지지 않은 판단이 스무 개쯤 나옵니다. 에이전트에게 결정 트리를 달라고 한 이유입니다.

에이전트가 펼쳐준 질문은 이랬습니다.

```text
수강 신청 기능에서 결정할 질문
├─ 정원 판정은 어느 시점에 할까?
│   ├─ 신청 버튼을 누른 즉시 → 동시 신청이 몰리면 어떻게 막을까
│   │   ├─ DB 잠금을 걸까, 낙관적 버전으로 밀어낼까
│   │   └─ 초과 신청은 대기열로 남길까, 바로 실패시킬까
│   │       └─ 대기열에 남긴다면 → 정원이 나면 어떤 순서로 확정할까
│   └─ 결제 완료 시점 → 그 사이에 취소하면 어떻게 되나
│       └─ 정원이 이미 찬 상태라면 → 그 사람은 어디로 갈까
├─ 시간 충돌은 누가 막게?
│   ├─ 화면에서 막을까, 서버에서도 막을까
│   │   └─ 서버에서 막는다면 → 어떤 상태 코드로 돌려줄까
│   │       └─ 이미 결제한 뒤면 → 강좌 변경과 환불 중 무엇을 남길까
│   └─ 강좌 목록을 언제 다시 그릴까
│       └─ 이미 신청한 상태라면 → 경고만 보여줄까
├─ 환불 금액은 언제 확정할까?
│   ├─ 취소 시점에 계산할까
│   │   └─ 계산 기준이 나중에 바뀌면 → 이미 환불한 금액을 어떻게 되돌릴까
│   └─ 결제 시점에 미리 확정해 둘까
│       └─ 미리 확정하면 → 출석 판정이 나중에 바뀌면 어떻게 갱신할까
├─ 출석은 언제 기록하나?
│   ├─ 수업 시간에 실시간으로 → 지각과 결석을 언제 확정할까
│   │   └─ 확정을 못 하면 → 정산에 어떤 값을 쓸까
│   └─ 수업이 끝난 뒤 일괄으로
│       └─ 정산이 이미 나갔으면 → 정산 주기를 다시 열어야 할까
└─ 중도 포기는 데이터를 어떻게 남길까?
    ├─ 취소 레코드를 새로 만들까
    │   └─ 만들면 → 원래 신청 레코드와 어떤 관계로 묶을까
    │       └─ 묶는 기준이 뭐냐에 따라 조회 쿼리가 달라진다
    └─ 상태 값만 바꾸자
        └─ 바꾸면 → 이력은 어디에 남을까
```

실제로 확정한 정책이 아니라 형태를 보여주려고 줄인 예시입니다. 갈래 끝에 남는 건 답이 아니라 제가 정해야 할 항목입니다. 트리는 답을 골라주지 않았고, 결정이 필요한 지점만 드러냈습니다.

이 트리를 받고 나서야 알았습니다. "수강 신청 기능 만들어줘"라는 한 문장 안에 이만큼의 결정이 숨어 있었습니다. 처음 펼쳐진 건 두 단계짜리였는데, "정원은 언제 판정하냐"를 물으니 동시 신청 처리와 대기열이 나왔고, "환불은 언제 계산하냐"를 물으니 정산 주기까지 나왔습니다. 묻는 만큼 가지가 깊어졌습니다.

혼자 머릿속으로 떠올렸다면 정원이 남았는지, 시간이 겹치는지 정도만 생각하고 넘어갔을 겁니다. 동시 신청을 막는 방법, 출석 확정 시점, 취소 이력의 관계는 코드를 짜기 시작하고 나서야 드러났을 문제입니다.

조건을 하나 더 넣으면 가지가 새로 생겼고 그 가지에서 앞서 빠뜨린 정책이 튀어나왔습니다. 제가 에이전트를 시뮬레이터처럼 썼다는 말은 이런 뜻입니다. 정해진 조건 안에서 가능한 경우를 넓게 펼쳐보고 사람이 결정할 지점을 찾는 일이었습니다.

## 가지치기

트리를 받았다고 바로 구현할 수 있는 건 아니었습니다. 위의 수강 예시만 봐도, 정원을 버튼을 누른 순간에 판정할지 결제 완료 시점에 판정할지부터 정해야 했습니다. 에이전트는 각 선택이 다른 조건과 충돌하는지 살펴줬지만 실제 서비스에서 필요한 흐름을 알려면 프로젝트 상황을 더 넣어야 했습니다.

그래서 지금 필요 없는 가지를 쳐냈습니다. 남긴 가지에는 조건을 더 붙였습니다. 그 조건을 다시 입력으로 넣으면 트리가 또 바뀌었습니다. 처음엔 안 보이던 예외가 드러나기도 했고 반대로 여러 갈래가 하나의 정책으로 정리되기도 했습니다.

몇 번을 반복하고 나서야 알았습니다. 가능성을 전부 채택하면 구조가 불필요하게 커지고 눈앞의 요구사항만 남기면 나중 변화에 취약해집니다. 어디까지 남길지는 시뮬레이션과 현실 조건을 같이 놓고 정해야 했습니다.

마지막까지 남는 문제는 언제 멈추느냐였습니다. 이것도 사람이 정해야 했습니다.

---

## 빠뜨린 조건

처음부터 컨텍스트를 완벽하게 전달한 건 아니었습니다. 돌려보면 제가 말하지 않은 조건이 선택지로 올라와 있었습니다. 동시 신청을 막는 수단을 고르는 조건이 그랬습니다. 그걸 보고서야 아, 이걸 말해야 했구나 싶었습니다.

조건을 보태서 다시 돌리면 결과가 달라졌습니다. 이 반복이 스펙을 구체화하는 실제 방식이었습니다. 문서를 먼저 완성해두고 검토를 맡긴 게 아니라, 대화와 시뮬레이션을 오가며 조금씩 확정해갔습니다.

여기서 얻은 게 하나 있습니다. 제가 무엇을 놓쳤는지는 결과를 봐야 알 수 있었습니다. 머릿속으로 점검하는 것보다 어긋난 결과를 눈으로 보는 쪽이 빨랐습니다.

---

## 문서로 남기기

스펙이 정해지는 동안 새 맥락도 계속 생겼습니다. 어떤 가지를 잘랐는지뿐 아니라 왜 잘랐는지, 어떤 조건에서 예외를 허용했는지까지 다음 판단에 영향을 줬습니다. 사람이 그 맥락을 매번 처음부터 다시 넣어줄 수는 없습니다. 대화가 바뀌고 작업자가 바뀌면 머릿속에 있던 조건은 그대로 사라집니다.

그래서 알아낸 것을 그때그때 문서에 쌓았습니다. 요구사항은 무엇이 필요한지, 정책은 어떤 조건에서 무엇을 지켜야 하는지, 결정 기록은 왜 그 방향을 택했는지를 담았습니다. 한 번 정리하고 끝나는 문서는 아니었습니다. 새 조건이 나오고 작은 결정이 내려질 때마다 해당 문서에 내용을 더했습니다. 1부에서 문서를 준비한 뒤에도 기록이 계속 필요했던 이유입니다.

여기서 고민이 하나 생겼습니다. 결정의 결과만 남기면 문서가 짧고 읽기 쉽습니다. 대신 왜 그렇게 정했는지가 빠집니다. 다음 작업에서는 같은 지점을 다시 고민하게 됩니다.

과정을 전부 남기면 이벤트 소싱에 가까워집니다. 무엇이 언제 바뀌었는지 순서대로 남습니다. 재구성은 쉽지만 기록이 계속 불어납니다. 읽는 사람은 지금 유효한 내용을 골라내야 합니다.

그래서 모든 대화를 옮겨 적지는 않았습니다. 다음 판단을 바꿀 만한 조건과 이유만 결정 문서에 남겼습니다. 나머지는 요구사항과 정책 문서의 현재 상태로 정리했습니다.

이렇게 쌓아둔 기록이 다음 작업의 출발점이 됐습니다. 앞선 대화를 모르는 에이전트가 같은 자리에서 다른 정책을 구현하지 않으려면, 대화 밖에 남은 내용이 있어야 했습니다.

## 사람이 한 일

문서가 어느 정도 갖춰지면 남는 일은 승인뿐이라고 생각하기 쉽습니다. 이번 프로젝트는 그 지점에서 어긋났습니다. 가지를 자르던 순간에도, 구현이 한창일 때에도 에이전트에 없는 맥락이 필요해졌습니다.

빈틈이 드러나면 대화로 돌아가 조건을 보태고 다시 검토했습니다. 새로 확정된 내용은 문서에 남겼습니다.

제가 맡은 자리는 현실과 에이전트 입력 사이에 남는 빈틈이었습니다. 답을 혼자 만들어낸 것도 아니었고 에이전트가 낸 답을 그대로 옮겨 적은 것도 아니었습니다. 아직 전달되지 않은 것이 무엇인지 찾아내고 다음 작업에도 빠지지 않게 남겨두는 일이었습니다.

---

## 이번 프로젝트에서의 AI Native

AI Native라는 말에 정해진 정의가 있는 건 아니었습니다. 이번 프로젝트에서는 코드를 얼마나 AI가 썼는지보다, 요구사항 검토부터 스펙 수립, 구현과 검증까지 이어지는 흐름에 AI를 어떻게 끼워 넣을지로 해석했습니다. 사람이 스펙을 완성한 뒤 넘기는 대신, 스펙을 만드는 과정부터 같이 해봤습니다.

이 해석이 유일한 답이라고 생각하지는 않습니다. 이번 프로젝트에서 해본 시도에 가깝습니다. 돌아보면 역할은 자연스럽게 갈렸습니다. 에이전트가 선택지를 정리하고 확정된 내용을 구현했고 제가 현실의 조건과 우선순위를 판단했습니다.

## 마치며

돌아보면 에이전트는 사람을 대체했다기보다 일의 속도를 올려준 도구에 가까웠습니다. 속도가 올라간 만큼 제가 놓친 맥락도 빨리 드러났습니다.

다음 글에서는 코드 작성으로 넘어가겠습니다. 개발자의 본업 중 가장 큰 비중을 차지하는 영역에서 에이전트가 어디까지 맡았고, 사람의 역할이 어떻게 달라졌는지 이야기해보겠습니다.
