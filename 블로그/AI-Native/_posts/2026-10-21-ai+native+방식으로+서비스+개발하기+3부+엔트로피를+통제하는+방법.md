## Intro

2부에서는 AI가 잘한 일과 못 한 일을 나눠 보았습니다. 요구사항을 시뮬레이션하고 코드를 빠르게 짜는 쪽은 좋았습니다. 반면 합의한 의미와 컨벤션을 끝까지 유지하는 일은 AI가 스스로 보장하지 못했습니다.

코드를 빠르게 생산하는 환경이라서 이 문제가 더 크게 드러났습니다. 작은 규칙 위반이나 결정사항 누락도 빠르게 여러 곳으로 복제되기 때문입니다.

이번 글에서는 이 문제를 **프로젝트 엔트로피**로 정리해 보겠습니다. 엔트로피가 늘지 않게 하려면 어떤 장치를 두어야 했는지 이야기해 보겠습니다.

---

## 엔트로피란 무엇인가

엔트로피는 원래 물리학 용어입니다. 흩어지기 쉬운 상태를 가리키는 말인데, 소프트웨어 공학에서는 레먼이 1974년에 먼저 가져다 썼고, 헌트와 토머스가 1999년 『실용주의 프로그래머』에서 개념으로 정리했습니다.

> 소프트웨어 개발은 거의 모든 물리 법칙에서 자유롭지만, 엔트로피만큼은 정면으로 맞습니다. 엔트로피는 시스템의 무질서량을 가리키는 물리학 용어입니다. 소프트웨어에서 무질서가 늘어나면 프로그래머들은 이를 소프트웨어 썩음이라 부릅니다.

---

## 이 글에서 말하는 프로젝트 엔트로피

저는 이 말을 프로젝트의 일관성을 가리키는 데 씁니다. 같은 역할을 하는 코드가 서로 다른 스타일과 컨벤션을 갖게 된 상태가 프로젝트 엔트로피가 높은 상태입니다. 같은 문제를 해결하는 코드인데도 책임의 위치, 이름을 짓는 방식, 예외를 처리하는 방법, 테스트를 작성하는 방식이 제각각으로 나뉩니다.

---

## 엔트로피는 속도가 문제입니다

이런 차이 하나만 보면 국소적인 문제처럼 보입니다. 특정 파일을 수정하거나 기능 하나를 추가할 때 잠깐 더 판단하면 해결할 수 있는 문제처럼 느껴집니다. 진짜 문제는 차이가 생기는 속도입니다. 제각각인 코드가 다음 작업의 참고 코드가 됩니다. 그 코드가 다시 새로운 작업에 복제되면서 같은 종류의 차이가 더 빠르게 생깁니다. 이 과정이 반복되면 증가 속도 자체가 지수적으로 커질 수 있습니다.

엔트로피가 통제되지 않은 채 계속 증가하면 프로젝트는 유지보수하기 어려운 수준을 넘어 사실상 유지보수가 불가능해집니다. 어떤 구조와 규칙을 따라야 하는지 판단할 수 없고 새로운 변경이 기존의 여러 예외와 충돌하기 때문입니다. 그 상태에서는 프로젝트가 정상적으로 지속되기 어렵습니다.

반대로 엔트로피가 낮은 프로젝트는 같은 역할을 하는 코드가 마치 템플릿 엔진으로 찍어낸 것처럼 비슷한 구조와 흐름을 가집니다. 파일의 위치와 책임이 예측 가능합니다. 이름·예외 처리·테스트 방식도 일정한 규칙 안에서 반복됩니다. 새로운 작업을 시작할 때마다 설계를 처음부터 다시 고민하지 않아도 됩니다.

AI를 쓴다고 엔트로피가 자동으로 오르지는 않습니다. 다만 AI의 생산 속도가 빠른 만큼, 일관성을 관리하지 않으면 제각각인 코드와 그로 인한 엔트로피도 빠르게 복제될 수 있습니다.

---

## 빠른 코드 생산은 빠른 복제를 의미합니다

에이전트는 세션에 쌓인 것을 기준으로 다음 코드를 만듭니다. 주고받은 대화, 읽은 파일, 직전에 만든 출력이 모두 다음 출력의 재료가 됩니다. 어긋난 출력이 한 번 컨텍스트에 들어오면, 그 다음 출력도 같은 방향으로 어긋나기 쉽습니다. 고치기 전까지 같은 모양이 복제되는 구조입니다.

처음에는 작은 차이로 시작합니다.

- 같은 개념을 다른 이름으로 부릅니다.
- 비슷한 정책을 서로 다른 위치에서 처리합니다.
- 기존 컨벤션과 다른 방식으로 새 코드를 작성합니다.
- 이전에 합의한 예외 조건을 구현에서 누락합니다.

세션 수에 따라 확산 양상이 달라집니다.

- **단일 세션**: 기준이 되는 컨텍스트가 하나라 어긋남이 같은 방향으로 반복됩니다. 컨텍스트를 바로잡으면 이후 출력에 반영되므로 전파가 멈춥니다.
- **병렬 세션**: 세션마다 다른 시점의 코드와 대화를 기준으로 생성하므로, 같은 규칙 위반도 세션마다 다른 형태로 굳어집니다. 한 세션의 수정이 다른 세션에 자동으로 들어가지 않으므로, 벌어지는 속도가 고치는 속도를 앞지르기 쉽습니다.

---

## 남겼는데도 누락됩니다

결정을 문서와 컨텍스트로 남기고 계획까지 세웠지만, 구현에서 빠지는 일이 있었습니다. 대화에서 합의한 컨벤션을 다음 작업에서 에이전트가 놓칩니다. 이전 작업에서 정한 책임의 경계를 새로운 코드가 침범합니다. 테스트를 통과시키는 과정에서 요구사항에 없던 임시적인 예외 처리가 들어갑니다.

남긴 문서가 읽히지 않은 것입니다. 세션이 바뀌면 대화 맥락이 사라지고, 에이전트는 눈앞의 파일과 지시만 기준으로 삼습니다. 이런 누락은 코드 한 곳만 보면 발견하기 어렵습니다. 전체 구조와 이전 결정사항을 함께 봐야 알 수 있습니다.

그래서 결정을 코드가 반드시 거쳐 가는 자리에 두었습니다. 문서 종류마다 남는 테스트 레벨을 정했습니다.

- **유저스토리는 E2E 시나리오로**: 어떤 사용자 흐름을 끝까지 보장해야 하는지 시나리오로 먼저 고정했습니다.
- **정책 문서의 불변식은 도메인 서술 테스트로**: 각 테스트에서 어떤 업무 시나리오가 발생하고 어떤 도메인 규칙이 적용되며 결과가 어떻게 달라져야 하는지가 읽히도록 했습니다.
- **결정 문서의 선택은 테스트 이름과 구조로**: 허용·금지되는 상태 변화가 테스트 이름에 드러나도록 했습니다.

대화 세션에서 개발을 시작하기 전에 E2E 시나리오를 먼저 정리해 별도로 남겼습니다. 세션이 종료되면 코드 변경은 남아도, 대화 중 공유한 전체 시나리오와 의도까지 함께 남지는 못했습니다. 이후 작업에서는 그 시나리오를 기준으로 테스트와 구현을 이어갔고, 배포 후에도 실제 환경에서 기능이 의도대로 동작하는지 확인하는 기준으로 썼습니다.

TDD처럼 볼 수도 있지만, 실제로는 DDD와 컨텍스트를 코드로 옮긴 것에 가깝습니다. 예를 들어 테스트 이름부터 다음처럼 달랐습니다.

```ts
describe('수강 신청', () => {
  it('수강 가능한 강좌를 신청하면 수강 상태가 신청 완료로 변경된다', async () => {
    // given: 학습자가 수강 가능한 강좌를 확인한다.
    // when: 강좌 수강을 신청한다.
    // then: 수강 상태가 신청 완료로 변경된다.
  });

  it('이미 수강 중인 강좌를 다시 신청할 수 없다', async () => {
    // given: 학습자가 이미 해당 강좌를 수강 중이다.
    // when: 같은 강좌를 다시 신청한다.
    // then: 중복 신청 오류가 발생하고 수강 상태는 변하지 않는다.
  });
});
```

이 테스트는 구현 방법보다 도메인 규칙을 먼저 보여줍니다. 내부 구조가 바뀌더라도 수강 신청이라는 업무 시나리오와 허용·금지되는 상태 변화는 같은 기준으로 확인할 수 있습니다.

테스트 항목을 읽는 것만으로도 다음 작업자가 현재 도메인에서 지켜야 할 규칙을 파악할 수 있었습니다.

## 우리는 무엇을 남겨야 할까?

프로젝트에서 남기고 관리한 것은 세 층이었습니다.

1. **무엇을 만들지** — 문제 정의층입니다. 바뀌기 쉬운 층이라, 바뀔 때마다 아래 두 층을 다시 검토하게 만드는 입력이었습니다.
    - **요구사항**: 구현 방법이 아니라 도메인 관점에서 필요한 순수한 요구사항만 남겼습니다.
    - **유저스토리**: 요구사항을 실제 사용자의 흐름으로 풀어 액터와 도메인 행위를 찾았습니다. E2E 시나리오로 고정했습니다.
2. **어떻게 만들지** — 판단 고정층입니다. 이 글의 엔트로피 정의와 직접 연결되는 층이라, 비어 있으면 같은 역할을 하는 코드가 제각각으로 갈라졌습니다.
    - **정책 문서(불변식)**: 행위별 조건과 반드시 지켜야 할 규칙, 조건이 겹칠 때의 우선순위를 정했습니다. 도메인 서술 테스트로 남겼습니다.
    - **결정 문서**: 선택한 내용과 이유, 검토한 대안을 기록했습니다. 현재 유효한 결정만 유지하고 테스트 이름과 구조로 남겼습니다.
3. **어떻게 강제할지** — 집행층입니다. 위 두 층의 내용을 코드에 박아 넣는 장치였습니다.

```text
3. 어떻게 강제할지 (집행층, 2층을 코드에 박는 장치)
├─ 텍스트 기준 (알려주는 것 — 해석이 갈릴 수 있음)
│  ├─ 단일 규칙 파일
│  │  ├─ 명명·스타일
│  │  │  └─ 파일명, 코드 스타일, 네이밍, 타입 사용, 반복 구현 패턴
│  │  ├─ 구조·책임
│  │  │  └─ 폴더·파일·모듈 책임, 도메인별 배치
│  │  │  └─ Aggregate 소유권·내부 접근 경로
│  │  ├─ 계층·경계
│  │  │  └─ 의존 방향, 직접 참조 금지, ACL, import 방향
│  │  ├─ 타입 계약
│  │  │  └─ DTO·Domain·Presentation 분리, Payload·Cross-BC 경계
│  │  ├─ 실행 원칙
│  │  │  └─ 상태 변경·데이터 접근·오류 처리, 비동기 처리, 금지 API·패턴
│  │  ├─ 외부 약속
│  │  │  └─ API 스키마·데이터 모델·외부 노출 계약
│  │  ├─ 운영 기준
│  │  │  └─ 설정·외부 시스템·보안, 실행 환경별 허용 범위
│  │  └─ 작업 절차
│  │     └─ 변경 방법, 검증·예외 처리, 완료 조건
│  ├─ 컨텍스트·결정 문서 참조
│  │  └─ 도메인·사용자·테넌트 배경, 현재 유효 결정
│  └─ 작업 전 장치: 규칙 재주입, E2E 시나리오 고정
│     └─ 잘못된 출발 방지
├─ 기계 검증 (막는 것 — 해석 여지 없이 판정)
│  ├─ ESLint
│  │  └─ 스타일·경로·import 방향·외부 계약·오류 처리·경계 침범
│  ├─ AST 아키텍처 검사
│  │  ├─ UseCase 역할·트랜잭션 경계, 표준 구조·호출 방식
│  │  ├─ Domain 순수성·생명주기, Aggregate 소유권
│  │  ├─ 영속성·이벤트 허용 범위, 계층 계약·산출물 동기화
│  │  ├─ 타입 경계, 테넌트·권한 조건
│  │  └─ 스키마·마이그레이션 호환성, Outbox·외부 연동 제약
│  ├─ 테스트·빌드
│  │  └─ 도메인 테스트, TypeScript 검사, lint → 검사 → 테스트 → 빌드
│  ├─ 예외 관리
│  │  └─ 위반은 파일·줄 단위로 기록, 예외 사유를 코드에 명시
│  └─ CI 게이트: 전부 통과하지 못하면 머지 불가
│     └─ 사람이 놓친 것도 최후에 차단
└─ 사람 판단 (판정하는 것 — 앞의 둘이 못 잡는 의도·맥락·예외)
   ├─ 자기검토
   │  └─ 요구사항 반영·규칙 위반·컨벤션 일관성
   │  └─ 개념 중복·경계 침범·예외 근거
   ├─ 단계별 게이트
   │  └─ 시나리오 채택·일반화 수준·용어 충돌·유지 여부·다음 단계 승인
   └─ 반복 수정 루프
      └─ 위반 커밋으로 가드레일 검증, 원인·파급·규칙 보완 판단 후 수정
```

그런데 이 세 번째 층이 엔트로피를 높이는 주범이기도 했습니다. 에이전트는 이미 있는 것을 찾아 쓰기보다 새로 만드는 쪽을 택하기 쉽습니다. 흔한 실수는 다음과 같습니다.

- 있는 유틸리티를 두고 비슷한 함수를 새로 만듭니다.
- 다른 파일에 같은 개념의 타입을 다시 정의합니다.
- 정해진 계층을 우회해 직접 참조하는 지름길을 만듭니다.
- 예외 처리를 그때그때 다른 방식으로 추가합니다.
- 테스트를 기존 구조와 다른 모양으로 새로 짭니다.

폴더 레벨과 파일 레벨까지 역할과 책임이 명확하지 않으면, 무엇을 어디에서 찾아야 하는지 모르고 같은 개념을 다른 자리에 다시 만듭니다. 분류가 되어 있어야 재사용이 되고, 재사용이 되어야 같은 역할의 코드가 한 모양으로 모입니다.

선언으로 끝나는 1번과 2번과 달리, 3번은 코드와 절차라서 스스로 낡습니다. 규칙 파일은 비대해지고, 검사는 현실을 따라가지 못하고, 게이트는 우회와 예외를 낳습니다. 기준이 늘어날수록 에이전트가 읽어야 할 것도 늘고, 기준끼리 어긋나면 막으려던 불일치를 집행 장치가 직접 만듭니다. 그래서 3번은 많을수록 좋은 것이 아니라, 적고 기계적일수록 좋은 층이었습니다.

다음은 엔트로피를 낮추기 위해 시도한 것들을 소개합니다.

---

## 프로젝트의 구현 규칙을 한 곳에 모았습니다

프로젝트 전체에 적용되는 에이전트 행동 규칙은 하나의 단일 규칙 파일로 유지했습니다. 이 파일에는 도메인의 세부 결정이나 정책을 모두 넣지 않았습니다. 도메인과 관련된 결정사항은 별도의 도메인 결정 문서로 관리했습니다.

단일 규칙 파일을 쓴 이유는 정적 검사만으로는 부족했기 때문입니다. 검사로 잡고 고치는 데는 비용이 듭니다. 규칙을 먼저 명세해두면 에이전트는 실수하기 전에 기준을 보고, 설계할 때도 참고할 내용이 분명해집니다. 실수하고 되돌리는 것이 가장 비싼 비용이라서, 처음부터 잘 짜게 만드는 쪽이 제일 쌉니다.

단일 규칙 파일에는 에이전트가 코드를 작성하고 수정할 때 따라야 하는 기준을 담았습니다. 실제 파일에는 이보다 훨씬 많은 세부 규칙을 정의했지만 크게 나누면 다음과 같은 내용입니다.

- 프로젝트 구조와 폴더·파일·모듈의 책임
- 파일명, 코드 스타일, 반복해서 사용할 구현 패턴
- 계층·모듈·도메인 사이의 경계와 의존 방향
- API·데이터 모델·외부 노출에 대한 계약
- 상태 변경·데이터 접근·오류 처리와 같은 실행 원칙
- 설정·외부 시스템·보안 등 운영 중 지켜야 할 기준
- 작업 절차·변경 방법·검증·예외 처리와 완료 조건

이 목록은 에이전트가 무엇을 지키는지에 대한 골격입니다. 여기에 도메인별 예외 상황이나 협업 방식 같은 맥락은 넣지 않았습니다. 그런 판단은 이 파일이 아니라 결정 문서에 남겼습니다.

실제 규칙은 이보다 훨씬 구체적이었습니다. 예를 들면 다음과 같은 규칙을 정의했습니다.

- Domain 계층에서 프레임워크나 Infrastructure 라이브러리를 직접 import하지 않습니다.
- 서로 다른 Bounded Context를 직접 참조하지 않고 정해진 계약과 ACL을 통해 연결합니다.
- Command UseCase는 정해진 transaction 설정과 EntityManager 주입 조건을 함께 지켜야 합니다.

도메인 결정 문서가 무엇을 만들고 왜 그렇게 결정했는지를 기록한다면, 단일 규칙 파일은 에이전트가 그 결정을 어떤 구조와 방식으로 코드에 반영해야 하는지를 정하는 문서였습니다.

규칙 파일의 목적은 AI에게 좋은 코드를 작성하라고 추상적으로 요청하는 것이 아니었습니다. 에이전트가 프로젝트 안에서 어떤 행동을 해야 하고 어떤 행동을 피해야 하는지를 구체적으로 제한하는 것이었습니다.

## 규칙을 잃어버리는 경우

규칙 파일이 있어도 에이전트는 규칙을 잃어버립니다. 대화가 길어지면 앞부분의 지시가 뒤로 밀려나고, 작업 범위가 커지면 현재 작업과 무관해 보이는 규칙부터 빠집니다. 파일에 적혀 있다는 사실과 에이전트가 그 순간 기준으로 삼고 있다는 것은 다릅니다.

어려운 점은 에이전트 스스로 이걸 판단하지 못한다는 것입니다. 자기 컨텍스트 안에 전체 규칙이 들어 있는지, 무엇이 빠졌는지 확인할 근거가 에이전트에게는 없습니다. 잃어버린 쪽이 잃어버렸다는 사실을 모릅니다. 물어봐도 다 있다고 답합니다.

그래서 일단 컴팩션이 일어나면 규칙을 다시 탑재하도록 했습니다. 에이전트의 판단에 맡기지 않고 사람이 정한 시점에 바깥에서 넣어주는 방식입니다.

이 과정은 다소 반복적으로 느껴질 수 있습니다. 하지만 같은 내용을 다시 전달하는 비용보다, 규칙 없이 만든 코드를 되돌리는 비용이 더 컸습니다. 잃어버리기 전에 다시 주는 쪽이 쌉니다.

---

## 컨텍스트와 결정사항을 기록했습니다

규칙만으로는 프로젝트의 모든 배경을 전달할 수 없습니다. 그래서 프로젝트의 도메인, 사용자, 테넌트, 정책, 제약사항을 별도의 컨텍스트 문서로 정리했습니다. 규칙 파일처럼 매번 읽고 따르게 한 것은 아닙니다. 배경을 알고 나면 세부 판단은 에이전트에 어느 정도 맡기는 편이 낫다고 봤습니다.

기술적 결정도 기록했습니다. 결정사항에는 무엇을 결정했는지뿐 아니라, 왜 그렇게 결정했는지, 어떤 대안을 검토했는지, 이후 코드에 어떤 영향을 주는지를 함께 남겼습니다.

결정사항을 많이 쌓는 데 집중하지 않았습니다. **현재 유효한 결정이 무엇인지 분명하게 유지하는 것**에 집중했습니다.

같은 주제에 새로운 결정이 생기면 이전 결정을 지우거나 덮어쓰지 않고 새 결정이 기존 결정을 대체한다는 관계를 기록했습니다. 이후 작업에서는 과거의 모든 결정을 동일하게 참고하지 않고 현재 유효한 결정을 기준으로 삼았습니다.

이 기록은 과거의 대화를 보관하는 용도가 아니었습니다. 다음 작업에서도 같은 선택과 제약을 재현하기 위한 현재의 기준이었습니다.

대화창의 기억에 의존하면 시간이 지나거나 작업 범위가 바뀔 때 중요한 내용이 사라질 수 있습니다. 결정사항과 그 효력 관계를 문서로 남기면 사람과 에이전트가 어떤 결정이 아직 유효한지 다시 확인할 수 있습니다.

## 에이전트에게 자기검토를 맡겼습니다

구현이 끝난 뒤 에이전트가 알아서 자기검토를 시작하지는 않았습니다. 사람이 명시적으로 검토를 요청하고 어떤 기준으로 확인해야 하는지도 함께 전달했습니다.

단순히 “문제가 없는지 확인해줘”라고 요청하지 않았습니다. 다음과 같이 검토 범위를 구체적으로 지정했습니다.

- 합의한 요구사항이 모두 반영되었는가?
- 프로젝트 규칙을 위반한 부분이 있는가?
- 기존 코드의 컨벤션과 일관적인가?
- 비슷한 개념을 중복해서 만들지 않았는가?
- 권한과 테넌트 경계를 침범할 가능성이 있는가?
- 추가된 예외 처리가 실제 요구사항에 근거하는가?

AI가 자기검토를 완벽하게 수행하지는 못했습니다. 그래도 구현과 별도의 검토 단계를 사람이 명시적으로 만들고 반복하는 것만으로 누락을 발견할 가능성을 높일 수 있었습니다.

## 정적 검사도 함께 개발했습니다

규칙을 문서로만 적어두지는 않았습니다. 규칙이 추가될 때마다 가능한 부분은 정적 검사로 옮겼고, 정적 검사 자체도 프로젝트의 주요 개발 대상이 되었습니다.

자연어 지침만으로는 에이전트의 행동을 충분히 제약하기 어려웠습니다. 에이전트가 규칙을 읽고도 놓칠 수 있고, 같은 문장을 상황에 따라 다르게 해석할 수도 있습니다. 규칙 파일을 잘 작성하는 것만으로는 코드의 일관성을 보장하지 못했습니다.

그래서 정적 검사가 중요했습니다. 사람이 규칙을 다시 설명하거나 에이전트가 스스로 기억하기를 기대하는 대신, 코드가 규칙을 어겼는지를 기계적으로 확인하도록 만들었습니다.

ESLint에는 일반적인 TypeScript 오류와 코드 스타일뿐 아니라, 프로젝트의 구조를 지키기 위한 규칙을 추가했습니다. 크게 보면 다음과 같은 항목입니다.

- 코드 스타일·네이밍·타입 사용과 비동기 처리 방식
- 반복되기 쉬운 구현 습관, 파일 위치에 따른 경로와 실행 환경별 허용 범위
- 계층·모듈 사이의 import 방향과 Domain의 외부 의존성, 금지된 API와 테스트 작성 규칙
- 외부에 드러나는 계약과 오류 처리 방식
- 도메인 간 직접 참조와 ACL 경계, Aggregate·tenant·권한 경계 침범

ESLint만으로 표현하기 어려운 규칙은 TypeScript AST를 읽는 별도의 아키텍처 검사기로 만들었습니다. 이 검사기는 개별 문법보다 코드의 구조와 의미를 확인했습니다.

- Command·Query UseCase의 역할과 transaction 경계, UseCase·Repository의 표준 구조와 호출 방식
- Domain 계층의 순수성과 객체 생명주기, Aggregate 소유권과 내부 Entity 접근 경로
- 영속성·상태 변경·이벤트 처리의 허용 범위, 계층 간 계약과 서로 다른 산출물 사이의 동기화
- 도메인별 코드 배치와 책임 소유권, DTO·Domain 모델·Presentation 타입의 경계
- Tenant 격리와 권한 처리의 구조적 조건, API Schema·Migration·시간 데이터의 호환성
- 장기 실행 작업·Outbox·외부 연동의 구조적 제약

검사 결과는 파일과 줄 단위의 위반으로 남겼습니다. 예외가 필요한 경우에도 무조건 무시하지 않았습니다. 어떤 규칙을 왜 예외로 두는지 코드에 명시하도록 했습니다. 규칙을 우회하는 것보다 예외를 드러내고 검토할 수 있게 만드는 편이 장기적으로 안전했습니다.

이 검사들은 `lint`, 아키텍처 검사, TypeScript 검사, 테스트와 빌드로 이어지는 검증 흐름에 포함했습니다.

규칙 파일에 적힌 내용을 사람이 기억해서 지키는 방식보다, 코드가 규칙을 어기면 작업 과정에서 바로 드러나도록 만드는 방식에 가까웠습니다.

## 적대 리뷰를 주기적으로 돌렸습니다

검증에서 문제가 발견되면 바로 다음 기능으로 넘어가지 않았습니다. 사람이 작업 결과와 규칙 위반 여부를 확인하고, 필요한 경우 다시 에이전트에게 수정하도록 했습니다.

밤에 작업을 마치기 전에는 별도의 loop를 돌려 일부러 규칙을 위반하는 커밋들을 만들게 했습니다. 가드레일이 제대로 작동하는지 확인하려는 적대 리뷰입니다. 위반을 발견할 수 있는지, 검토가 실제로 막아내는지를 일부러 깨보면서 시험했습니다.

그 결과는 사람이 최종적으로 검토했습니다. 발견된 위반을 그대로 받아들이지 않고, 어떤 규칙을 보완해야 하는지와 코드에 어떤 수정을 반영해야 하는지를 판단했습니다. 검사 결과를 단순히 통과시키는 데서 끝내지 않고, 왜 위반이 생겼는지, 같은 문제가 다른 곳에도 존재하는지, 수정이 기존 규칙을 깨뜨리지는 않는지를 함께 확인했습니다. 이렇게 깨고 고치는 과정을 반복하면서 프로젝트의 엔트로피를 낮춰왔습니다. 적대 리뷰에서 발견된 위반은 다시 규칙과 정적 검사로 되먹였습니다. 깨뜨리고, 고치고, 막는 장치를 덧붙이는 진화 과정을 반복한 것입니다.

이 과정이 필요했던 이유는 단일 규칙 파일 자체가 완벽하지 않기 때문입니다. 규칙끼리 모순되거나 충돌하는 경우가 생깁니다. 새로 추가한 규칙이 기존 규칙과 어긋나기도 하고, 상황마다 다르게 읽히는 규칙도 있습니다. 적대 리뷰는 이런 규칙의 흠을 드러내는 자리이기도 했습니다.

이 검증은 로컬에서 확인하는 절차에 그치지 않았습니다. CI 단계에서도 lint·아키텍처 검사·TypeScript 검사·테스트·빌드를 통과하지 못하면 머지할 수 없도록 연결했습니다. 사람이 검토에서 놓친 규칙 위반도 머지 직전에 다시 걸러지도록 했습니다.

## 이 프로젝트 관점에서 본 AI Native란?

이 일련의 과정을 시도한 근본적인 배경에는 모델의 한계가 있었습니다.

한 번의 대화와 자연어 지침만으로는 프로젝트의 모든 컨텍스트와 결정사항을 에이전트에게 전달할 수 없었고 전달한 내용도 모델이 항상 같은 방식으로 해석하고 지킨다고 보장할 수 없었습니다.

이 프로젝트 관점에서 AI Native를 정의해보면, 에이전트가 참고할 텍스트 데이터를 정제하고 그 한계를 검증 장치로 보완하는 개발 방식에 가까웠습니다.

프로젝트 규칙, 컨텍스트, 현재 유효한 결정사항, E2E 시나리오, 도메인 테스트를 서로 연결해 다음 작업의 기준으로 사용했습니다.

다만 텍스트를 잘 작성하는 것만으로 에이전트가 모든 규칙을 지키게 만들 수는 없었습니다. 모델의 한계로 자연어 지침을 놓치거나 다르게 해석하는 경우가 있었고 그런 부분은 정적 검사·테스트·CI·사람의 검토처럼 다른 장치로 보완했습니다.

텍스트는 에이전트가 따라야 할 방향과 맥락을 제공하고 실행 가능한 검증 장치는 그 방향에서 벗어난 결과를 발견하고 막는 역할을 맡았습니다.

## 마치며

AI의 실수를 완전히 없애는 것은 현실적이지 않습니다. 실수가 프로젝트 전체로 퍼지기 전에 발견하고 차단하는 구조를 만드는 것이 중요합니다.

이번 프로젝트는 처음 두 사람이 참여해 시작했습니다. 이후 더 많은 사람이 참여하는 프로젝트로 성장했고 한 사람이 AI와 함께 개발하는 단계를 넘어 여러 사람이 여러 에이전트를 사용해 개발하고 유지보수하는 단계로 확장되었습니다.

혼자 개발하는 AI Native와 여러 사람이 함께 개발하는 AI Native는 난이도가 크게 달랐습니다.

혼자 개발할 때는 한 사람이 대부분의 맥락과 결정사항을 공유하고 있기 때문에, 에이전트가 그 사람의 의도에 맞게 움직이면 작업을 이어갈 수 있습니다.

하지만 협업 상황에서는 사람마다 이해하는 방식이 다르고 각자가 사용하는 에이전트의 응답과 구현도 달라질 수 있습니다.

에이전트뿐 아니라 함께 일하는 개발자들과도 같은 요구사항과 설계 방향을 공유하고 서로의 작업이 충돌하지 않도록 싱크를 맞춰야 했습니다.

개발자가 각자의 방식으로 해석할 여지를 많이 남겨둘수록 같은 기능이 서로 다른 구조와 컨벤션으로 구현될 가능성이 커지고 프로젝트의 엔트로피도 높아집니다.

그래서 개인의 맥락을 전제로 하지 않는, 여러 개발자와 여러 에이전트가 공유할 수 있는 규칙·컨텍스트·검증 체계가 필요했습니다.

이 글은 방법이 정답이라는 주장이 아닙니다. 다음 과정을 하나의 사례로 남기려는 기록입니다.

- 이 프로젝트에서 AI Native를 어떻게 정의했는가
- 그 정의를 실제 개발 과정에 어떻게 적용했는가
- 여러 사람과 여러 에이전트가 함께 일하기 위해 어떤 규칙과 검증 장치를 만들어갔는가

시간이 지난 뒤에도 이 방식은 여러 사람과 여러 에이전트가 함께 개발하고 유지보수하는 과정에서 유효하게 작동했습니다.

그런 의미에서 저는 이 시도를 성공했다고 회고하고 있습니다. 이 글은 그 과정을 돌아보며 정리한 기록입니다.

이번 경험에서 얻은 결론은 다음과 같습니다.

> AI Native의 핵심은 AI에게 코드를 맡기는 데 있지 않습니다. 사람과 에이전트가 같은 컨텍스트와 결정사항을 공유하고 규칙과 검증을 통해 서로 다른 구현이 프로젝트의 일관성을 무너뜨리지 않도록 만드는 데 있습니다.
