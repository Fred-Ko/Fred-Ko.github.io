## Intro

2부에서는 에이전트와 함께 요구사항을 검토하고, 결정한 내용을 문서로 남기는 과정을 이야기했습니다. 그런데 문서에 적어둔 결정이 다음 구현에 그대로 반영되지는 않았습니다.

한 곳에서 놓친 규칙을 고치기도 전에, 다른 곳에 비슷한 코드가 생겼습니다. 에이전트가 빠르게 코드를 만드는 만큼 어긋난 구현도 빠르게 늘어났고, 어느 쪽이 프로젝트의 기준인지 다시 확인해야 했습니다.

저는 이렇게 코드와 결정이 조금씩 서로 다른 방향으로 벌어지는 상태를 **프로젝트 엔트로피**라고 불렀습니다. 이 글에서는 그 차이를 어떻게 발견하고, 다음 작업으로 퍼지지 않게 했는지 이야기하겠습니다.

---

## 엔트로피?

엔트로피는 원래 물리학에서 쓰는 말입니다. 에너지나 물질이 한곳에 모여 있는 상태보다 여러 방식으로 퍼져 있는 상태가 얼마나 더 가능한지를 설명할 때 사용합니다. 일상에서는 질서가 흐트러지는 모습을 빗대어 말할 때도 쓰입니다.

소프트웨어에 빗댄 표현도 오래됐습니다. 앤드루 헌트와 데이비드 토머스는 1999년 출간한 [『실용주의 프로그래머』의 「Software Entropy」](https://www.informit.com/store/pragmatic-programmer-from-journeyman-to-master-9780201616224)에서 무질서가 늘어나는 소프트웨어의 상태를 “software rot”이라고 불렀습니다.

이 글에서 말하는 **프로젝트 엔트로피**도 비유입니다. 같은 역할을 하는 코드라면 어디에 두고 어떻게 작성할지 어느 정도 예상할 수 있어야 합니다.

그런데 비슷한 기능마다 책임을 두는 위치가 다르고, 이름·예외 처리·테스트 방식까지 제각각이면 다음 작업에서 무엇을 기준으로 삼아야 할지 알기 어려워집니다. 저는 이렇게 프로젝트 안의 기준이 갈라진 상태를 엔트로피가 높다고 표현했습니다.

---

## 빠른 코드 생산은 엔트로피 증가를 말한다

코드를 빠르게 만들수록 작은 어긋남도 빨리 쌓였습니다. 한 파일에서 끝날 것 같았던 차이가 다음 작업의 참고 코드가 됐기 때문입니다. 에이전트는 앞서 주고받은 대화와 읽은 파일, 방금 만든 결과물을 바탕으로 다음 코드를 작성했습니다. 잘못 잡힌 기준을 바로잡지 않으면 비슷한 구현이 다른 곳에도 생겼습니다.

처음에는 눈에 잘 띄지 않는 차이였습니다.

- 같은 개념을 다른 이름으로 부릅니다.
- 비슷한 정책을 서로 다른 위치에서 처리합니다.
- 기존 컨벤션과 다른 방식으로 새 코드를 작성합니다.
- 이전에 합의한 예외 조건을 구현에서 누락합니다.

작업을 여러 세션에서 진행하자 차이가 퍼지는 양상도 달라졌습니다.

- **단일 세션**에서는 잘못 잡힌 기준을 다음 코드에서도 반복했습니다. 기준을 바로잡은 뒤에는 그동안 만든 결과물도 다시 확인해야 했습니다.
- **병렬 세션**에서는 각 세션이 서로 다른 시점의 코드와 대화를 참고했습니다. 한쪽에서 규칙 위반을 고쳐도 다른 쪽은 이를 모른 채 작업을 이어갔습니다. 같은 문제를 서로 다른 방식으로 구현하는 경우도 생겼습니다.

사람이든 에이전트든 누가 작업하더라도 같은 규칙과 정책을 따라야 했습니다. 여러 개발자와 여러 세션에서 만든 코드가 한 프로젝트의 코드처럼 이어지게 하려면, 각자의 대화 밖에 공통의 기준을 남기고 실제 구현에서도 지키는 방법이 필요했습니다.

## 우리는 무엇을 남겨야 할까?

에이전트가 가장 자주 한 실수는 이미 있는 것을 찾기보다 비슷한 것을 새로 만드는 일이었습니다. 기존 유틸리티를 두고 함수를 다시 만들거나, 같은 개념의 타입을 다른 곳에 정의했습니다. 정해진 계층을 거치지 않고 바로 참조하는 코드도 생겼습니다. 각각은 당장 동작했지만, 같은 역할의 코드가 프로젝트 안에서 서로 다른 모습으로 늘어났습니다.

에이전트는 한 번 만든 결과물을 다음 작업의 기준으로 삼는 경향도 있었습니다. 처음부터 잘못된 구조로 만들면 이후 코드를 고치는 데 그치지 않고, 그 구조를 따라 만든 결과물까지 다시 살펴야 했습니다. 제 경험에서는 비용으로 보나 결과의 질로 보나, 첫 시도에서 프로젝트의 기준에 맞게 만드는 편이 가장 경제적이었습니다.

그래서 다음 작업에서도 같은 선택을 할 수 있도록 기준을 남겼습니다. 프로젝트에서 관리한 내용은 크게 세 층이었습니다.

1. **무엇을 만들지** — 요구사항에는 구현 방법보다 도메인에서 필요한 것을 적었습니다. 유저스토리로 실제 사용자의 흐름을 풀고, 끝까지 보장해야 할 동작은 E2E 시나리오로 남겼습니다.

2. **어떻게 만들지** — 정책 문서에는 행위의 조건과 반드시 지킬 규칙, 조건이 겹칠 때의 우선순위를 적었습니다. 결정 문서에는 선택한 내용과 이유, 검토한 대안을 남기고 현재 유효한 결정을 구분했습니다.

3. **어떻게 지킬지** — 에이전트가 참고할 규칙 파일을 두고, 테스트와 정적 검사로 확인할 수 있는 위반을 찾아냈습니다. 검사로 판단하기 어려운 의도와 예외는 사람이 검토했습니다.

이 가운데 제가 특별히 관리하려던 것은 **컨벤션과 구현 규칙**이었습니다. 파일명과 코드 스타일뿐 아니라 코드를 둘 위치, 모듈의 책임, 계층 사이의 의존 방향, 오류 처리 방식까지 포함했습니다. 이런 기준이 없거나 작업마다 다르게 적용되면, 에이전트는 제각각인 코드를 다시 참고해 비슷한 역할의 코드를 또 다른 방식으로 만듭니다. 그 차이가 쌓이는 것이 제가 말하는 프로젝트 엔트로피였습니다.

## 남겼는데도 제대로 작동하지 않았습니다

문서와 계획을 남겨도 다음 구현에서 결정이 빠지는 일이 있었습니다. 합의한 책임의 경계를 새 코드가 침범하거나, 테스트를 통과시키는 과정에서 요구사항에 없던 예외 처리가 들어갔습니다. 문서에 적는 것과 에이전트가 다음 작업에서 그 내용을 지키는 것은 다른 문제였습니다.

지켜야 할 내용이 서로 달랐기 때문에 확인하는 방법도 하나로 끝낼 수 없었습니다. 먼저 테스트로 옮길 수 있는 것부터 옮겼습니다.

- **유저스토리**에서는 끝까지 보장해야 할 사용자 흐름을 E2E 시나리오로 남겼습니다.
- **정책 문서**의 불변식은 조건에 따라 어떤 도메인 규칙이 적용되고 결과가 어떻게 달라지는지 테스트로 확인했습니다.
- **결정 문서**에서 허용하거나 금지한 상태 변화는 테스트 이름과 구조에 드러나게 했습니다.

개발을 시작하기 전에 E2E 시나리오를 따로 정리했습니다. 세션이 끝나도 다음 작업에서 그 시나리오를 기준으로 구현을 이어갈 수 있었고, 배포 후 실제 동작을 확인할 때도 사용했습니다. 도메인 규칙을 옮긴 테스트는 이름만 읽어도 어떤 상태 변화가 허용되는지 알 수 있도록 작성했습니다. 아래 코드는 그 이름과 서술 방식을 보여주는 예시입니다.

```ts
describe('수강 신청', () => {
  it('수강 가능한 강좌를 신청하면 수강 상태가 신청 완료로 변경된다', async () => {
    // given: 학습자가 수강 가능한 강좌를 확인한다.
    // when: 강좌 수강을 신청한다.
    // then: 수강 상태가 신청 완료로 변경된다.
  });

  it('이미 수강 중인 강좌를 다시 신청할 수 없다', async () => {
    // given: 학습자가 이미 해당 강좌를 수강 중이다.
    // when: 같은 강좌를 다시 신청한다.
    // then: 중복 신청 오류가 발생하고 수강 상태는 변하지 않는다.
  });
});
```

테스트는 사용자 흐름과 도메인 규칙을 확인하는 데 쓸 수 있었습니다. 하지만 코드가 어느 폴더에 있어야 하는지, 계층을 어떻게 거쳐야 하는지, 기존 패턴을 재사용했는지까지 이 테스트로 확인할 수는 없었습니다. 에이전트가 코드를 만들기 전에 참고할 구현 규칙도 필요했습니다.

## 프로젝트의 구현 규칙을 한 곳에 모았습니다

프로젝트 전체에 적용되는 에이전트 행동 규칙은 하나의 단일 규칙 파일로 유지했습니다. 이 파일에는 도메인의 세부 결정이나 정책을 모두 넣지 않았습니다. 도메인과 관련된 결정사항은 별도의 도메인 결정 문서로 관리했습니다.

단일 규칙 파일을 쓴 이유는 정적 검사만으로는 부족했기 때문입니다. 검사로 잡고 고치는 데는 비용이 듭니다. 규칙을 먼저 명세해두면 에이전트는 실수하기 전에 기준을 보고, 설계할 때도 참고할 내용이 분명해집니다. 실수하고 되돌리는 것이 가장 비싼 비용이라서, 처음부터 잘 짜게 만드는 쪽이 제일 쌉니다.

단일 규칙 파일에는 에이전트가 코드를 작성하고 수정할 때 따라야 하는 기준을 담았습니다. 실제 파일에는 이보다 훨씬 많은 세부 규칙을 정의했지만 크게 나누면 다음과 같은 내용입니다.

- 프로젝트 구조와 폴더·파일·모듈의 책임
- 파일명, 코드 스타일, 반복해서 사용할 구현 패턴
- 계층·모듈·도메인 사이의 경계와 의존 방향
- API·데이터 모델·외부 노출에 대한 계약
- 상태 변경·데이터 접근·오류 처리와 같은 실행 원칙
- 설정·외부 시스템·보안 등 운영 중 지켜야 할 기준
- 작업 절차·변경 방법·검증·예외 처리와 완료 조건

이 목록은 에이전트가 무엇을 지키는지에 대한 골격입니다. 여기에 도메인별 예외 상황이나 협업 방식 같은 맥락은 넣지 않았습니다. 그런 판단은 이 파일이 아니라 결정 문서에 남겼습니다.

실제 규칙은 이보다 훨씬 구체적이었습니다. 예를 들면 다음과 같은 규칙을 정의했습니다.

- `Domain` 계층에서 프레임워크나 `Infrastructure` 라이브러리를 직접 `import`하지 않습니다.
- 서로 다른 Bounded Context를 직접 참조하지 않고 정해진 계약과 ACL을 통해 연결합니다.
- `Command UseCase`는 정해진 `transaction` 설정과 `EntityManager` 주입 조건을 함께 지켜야 합니다.

도메인 결정 문서가 무엇을 만들고 왜 그렇게 결정했는지를 기록한다면, 단일 규칙 파일은 에이전트가 그 결정을 어떤 구조와 방식으로 코드에 반영해야 하는지를 정하는 문서였습니다.

규칙 파일의 목적은 AI에게 좋은 코드를 작성하라고 추상적으로 요청하는 것이 아니었습니다. 에이전트가 프로젝트 안에서 어떤 행동을 해야 하고 어떤 행동을 피해야 하는지를 구체적으로 제한하는 것이었습니다.

## 규칙을 잃어버리는 경우

규칙 파일이 있어도 에이전트는 규칙을 잃어버립니다. 대화가 길어지면 앞부분의 지시가 뒤로 밀려나고, 작업 범위가 커지면 현재 작업과 무관해 보이는 규칙부터 빠집니다. 파일에 적혀 있다는 사실과 에이전트가 그 순간 기준으로 삼고 있다는 것은 다릅니다.

어려운 점은 에이전트 스스로 이걸 판단하지 못한다는 것입니다. 자기 컨텍스트 안에 전체 규칙이 들어 있는지, 무엇이 빠졌는지 확인할 근거가 에이전트에게는 없습니다. 잃어버린 쪽이 잃어버렸다는 사실을 모르는 경우도 있었습니다. 실제로 규칙을 놓친 결과가 나왔는데도, 확인을 요청하면 규칙을 알고 있다고 답한 적이 있었습니다.

그래서 일단 컴팩션이 일어나면 규칙을 다시 탑재하도록 했습니다. 에이전트의 판단에 맡기지 않고 사람이 정한 시점에 바깥에서 넣어주는 방식입니다.

이 과정은 다소 반복적으로 느껴질 수 있습니다. 하지만 같은 내용을 다시 전달하는 비용보다, 규칙 없이 만든 코드를 되돌리는 비용이 더 컸습니다. 잃어버리기 전에 다시 주는 쪽이 쌉니다.

## 컨텍스트와 결정사항을 기록했습니다

규칙만으로는 프로젝트의 모든 배경을 전달할 수 없습니다. 그래서 프로젝트의 도메인, 사용자, 테넌트, 정책, 제약사항을 별도의 컨텍스트 문서로 정리했습니다. 규칙 파일처럼 매번 읽고 따르게 한 것은 아닙니다. 배경을 알고 나면 세부 판단은 에이전트에 어느 정도 맡기는 편이 낫다고 봤습니다.

기술적 결정도 기록했습니다. 결정사항에는 무엇을 결정했는지뿐 아니라, 왜 그렇게 결정했는지, 어떤 대안을 검토했는지, 이후 코드에 어떤 영향을 주는지를 함께 남겼습니다.

결정사항을 많이 쌓는 데 집중하지 않았습니다. **현재 유효한 결정이 무엇인지 분명하게 유지하는 것**에 집중했습니다.

같은 주제에 새로운 결정이 생기면 이전 결정을 지우거나 덮어쓰지 않고 새 결정이 기존 결정을 대체한다는 관계를 기록했습니다. 이후 작업에서는 과거의 모든 결정을 동일하게 참고하지 않고 현재 유효한 결정을 기준으로 삼았습니다.

이 기록은 과거의 대화를 보관하는 용도가 아니었습니다. 다음 작업에서도 같은 선택과 제약을 재현하기 위한 현재의 기준이었습니다.

대화창의 기억에 의존하면 시간이 지나거나 작업 범위가 바뀔 때 중요한 내용이 사라질 수 있습니다. 결정사항과 그 효력 관계를 문서로 남기면 사람과 에이전트가 어떤 결정이 아직 유효한지 다시 확인할 수 있습니다.

## 에이전트에게 자기검토를 맡겼습니다

구현이 끝난 뒤 에이전트가 알아서 자기검토를 시작하지는 않았습니다. 사람이 명시적으로 검토를 요청하고 어떤 기준으로 확인해야 하는지도 함께 전달했습니다.

단순히 “문제가 없는지 확인해줘”라고 요청하지 않았습니다. 다음과 같이 검토 범위를 구체적으로 지정했습니다.

- 합의한 요구사항이 모두 반영되었는가?
- 프로젝트 규칙을 위반한 부분이 있는가?
- 기존 코드의 컨벤션과 일관적인가?
- 비슷한 개념을 중복해서 만들지 않았는가?
- 권한과 테넌트 경계를 침범할 가능성이 있는가?
- 추가된 예외 처리가 실제 요구사항에 근거하는가?

AI가 자기검토를 완벽하게 수행하지는 못했습니다. 그래도 구현과 별도의 검토 단계를 사람이 명시적으로 만들고 반복하는 것만으로 누락을 발견할 가능성을 높일 수 있었습니다.

## 정적 검사도 함께 개발했습니다

규칙을 문서로만 적어두지는 않았습니다. 규칙이 추가될 때마다 가능한 부분은 정적 검사로 옮겼고, 정적 검사 자체도 프로젝트의 주요 개발 대상이 되었습니다.

자연어 지침만으로는 에이전트의 행동을 충분히 제약하기 어려웠습니다. 에이전트가 규칙을 읽고도 놓칠 수 있고, 같은 문장을 상황에 따라 다르게 해석할 수도 있습니다. 규칙 파일을 잘 작성하는 것만으로는 코드의 일관성을 보장하지 못했습니다.

그래서 정적 검사가 중요했습니다. 사람이 규칙을 다시 설명하거나 에이전트가 스스로 기억하기를 기대하는 대신, 코드가 규칙을 어겼는지를 기계적으로 확인하도록 만들었습니다.

ESLint에는 일반적인 TypeScript 오류와 코드 스타일뿐 아니라, 프로젝트의 구조를 지키기 위한 규칙을 추가했습니다. 크게 보면 다음과 같은 항목입니다.

- 코드 스타일·네이밍·타입 사용과 비동기 처리 방식
- 반복되기 쉬운 구현 습관, 파일 위치에 따른 경로와 실행 환경별 허용 범위
- 계층·모듈 사이의 `import` 방향과 `Domain`의 외부 의존성, 금지된 API와 테스트 작성 규칙
- 외부에 드러나는 계약과 오류 처리 방식
- 도메인 간 직접 참조와 ACL 경계, Aggregate·tenant·권한 경계 침범

ESLint만으로 표현하기 어려운 규칙은 TypeScript AST를 읽는 별도의 아키텍처 검사기로 만들었습니다. 이 검사기는 개별 문법보다 코드의 구조와 의미를 확인했습니다.

- Command·Query UseCase의 역할과 transaction 경계, UseCase·Repository의 표준 구조와 호출 방식
- Domain 계층의 순수성과 객체 생명주기, Aggregate 소유권과 내부 Entity 접근 경로
- 영속성·상태 변경·이벤트 처리의 허용 범위, 계층 간 계약과 서로 다른 산출물 사이의 동기화
- 도메인별 코드 배치와 책임 소유권, DTO·Domain 모델·Presentation 타입의 경계
- Tenant 격리와 권한 처리의 구조적 조건, API Schema·Migration·시간 데이터의 호환성
- 장기 실행 작업·Outbox·외부 연동의 구조적 제약

검사 결과는 파일과 줄 단위의 위반으로 남겼습니다. 예외가 필요한 경우에도 무조건 무시하지 않았습니다. 어떤 규칙을 왜 예외로 두는지 코드에 명시하도록 했습니다. 규칙을 우회하는 것보다 예외를 드러내고 검토할 수 있게 만드는 편이 장기적으로 안전했습니다.

이 검사들은 `lint`, 아키텍처 검사, TypeScript 검사, 테스트와 빌드로 이어지는 검증 흐름에 포함했습니다.

규칙 파일에 적힌 내용을 사람이 기억해서 지키는 방식보다, 코드가 규칙을 어기면 작업 과정에서 바로 드러나도록 만드는 방식에 가까웠습니다.

## 적대 리뷰를 주기적으로 돌렸습니다

검증에서 문제가 발견되면 바로 다음 기능으로 넘어가지 않았습니다. 사람이 작업 결과와 규칙 위반 여부를 확인하고, 필요한 경우 다시 에이전트에게 수정하도록 했습니다.

밤에 작업을 마치기 전에는 별도의 루프를 돌려 일부러 규칙을 위반하는 커밋들을 만들게 했습니다. 가드레일이 제대로 작동하는지 확인하려는 적대 리뷰입니다. 위반을 발견할 수 있는지, 검토가 실제로 막아내는지를 일부러 깨보면서 시험했습니다.

그 결과는 사람이 최종적으로 검토했습니다. 발견된 위반을 그대로 받아들이지 않고, 어떤 규칙을 보완해야 하는지와 코드에 어떤 수정을 반영해야 하는지를 판단했습니다. 검사 결과를 단순히 통과시키는 데서 끝내지 않고, 왜 위반이 생겼는지, 같은 문제가 다른 곳에도 존재하는지, 수정이 기존 규칙을 깨뜨리지는 않는지를 함께 확인했습니다.

이렇게 깨고 고치는 과정을 반복하면서 프로젝트의 엔트로피를 낮춰왔습니다. 적대 리뷰에서 발견된 위반은 다시 규칙과 정적 검사로 되먹였습니다. 깨뜨리고, 고치고, 막는 장치를 덧붙이는 진화 과정을 반복한 것입니다.

이 과정이 필요했던 이유는 단일 규칙 파일 자체가 완벽하지 않기 때문입니다. 규칙끼리 모순되거나 충돌하는 경우가 생깁니다. 새로 추가한 규칙이 기존 규칙과 어긋나기도 하고, 상황마다 다르게 읽히는 규칙도 있습니다. 적대 리뷰는 이런 규칙의 흠을 드러내는 자리이기도 했습니다.

이 검증은 로컬에서 확인하는 절차에 그치지 않았습니다. CI 단계에서도 lint·아키텍처 검사·TypeScript 검사·테스트·빌드를 통과하지 못하면 머지할 수 없도록 연결했습니다. 사람이 검토에서 놓친 규칙 위반도 머지 직전에 다시 걸러지도록 했습니다.

## 마치며

처음에는 두 사람이 참여해 시작한 프로젝트였습니다. 이후 참여자가 늘고 각자 여러 에이전트를 쓰게 되면서, 한 사람이 알고 있는 맥락을 전제로 작업을 이어갈 수 없었습니다. 같은 요구사항을 두고도 사람마다, 세션마다 다른 구현을 만들 수 있다는 점이 더 분명해졌습니다.

그래서 규칙과 현재 유효한 결정을 대화 밖에 남기고, E2E 시나리오와 도메인 테스트로 확인할 동작을 고정했습니다. 자연어 규칙을 놓치거나 다르게 해석하는 부분은 정적 검사와 CI에서 다시 확인했고, 의도와 예외는 사람이 판단했습니다. 함께 일하는 개발자들도 같은 기준을 확인할 수 있어야 했습니다.

제가 이 프로젝트에서 시도한 AI Native는 에이전트가 참고할 맥락을 정리하고, 서로 다른 구현이 한 프로젝트 안에서 갈라지지 않도록 계속 확인하는 방식이었습니다.

프로젝트가 커지고 참여자가 늘면 새 기능을 붙일 때 드는 비용도 빠르게 커질 거라고 생각했습니다. 그런데 시간이 지나도 기능을 추가할 때 체감한 기술적 구현 비용은 예상만큼 크게 늘지 않았습니다. 여러 사람과 에이전트가 같은 기준을 따라 작업을 이어갈 수 있었기 때문이라고 봅니다. 그래서 저는 이 시도를 성공했다고 회고합니다.

다음 글에서는 BE 안에서 효과를 본 방식이 왜 프로젝트 전체로는 이어지지 못했는지 이야기해 보겠습니다. 협업을 피할 수 없다면 그 과정에서 생긴 정보와 결정을 어디서부터 남기고, 다음 사람과 에이전트에게 어떻게 건네야 할까요? 이 질문을 따라가며 프로젝트 단위의 AI Native를 다시 생각해 보겠습니다.
